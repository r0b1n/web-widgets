Design document

The combobox on a MobX core

How combobox-web keeps its state after the rewrite: a frozen config and a props gate feed the selector stores, a Core turns them into one plain view model, and the views only render. Same properties, markup and behaviour as the released widget, with two bug fixes.

mendix/web-widgets #2572 Tests first: #2573 MobX 6.12.3 · brandi · downshift · floating-ui 257 unit tests · 5 snapshots unchanged

Principles

Six rules carry the whole design. Most of the code is the result of applying them consistently.

01

Static props are read once

Simple-type props never change for a widget instance. They go into a frozen ComboboxConfig at construction and are never observed.

02

Mendix values through a gate

Value objects change on every render. They live behind a DerivedPropsGate as observable.ref, read through plain getters so an in-place change is never hidden.

03

Derive, don't copy

Selectors and providers are computeds over the gate. The only state left is what the UI owns: search term, open flag, highlight, and a few loading latches.

04

Side effects are setup reactions

Datasource limit, filter, selection sync and keep-selection run in reactions registered with a setup host, started on mount and disposed on unmount.

05

No Mendix writes during render

Props reach the gate during render so that render shows them, but every reaction that writes to Mendix waits for React to commit.

06

Views never see MobX

Views get a plain vm snapshot through useSyncExternalStore, and call its commands. MobX never leaves the Core.

Decisions

The choices a reviewer is most likely to question, with the reasoning.

Why push props during render at all?rendering

So the render that receives new Mendix values also shows them, without a frame of stale data. The released widget did the same through updateProps.

The snapshot subscription ignores changes made by that push, because the same render reads the fresh snapshot anyway. Reporting it would schedule a React update while rendering.

Why a commit-phase flush and not a microtask?rendering

Reactions that write to Mendix take the setup host's schedule as their MobX scheduler. During a props push a run is queued; useLayoutEffect flushes the queue once React commits, still before paint. A render React replays or throws away writes nothing, and its queued runs happen at the next commit with the state of that moment.

Outside a props push the runs happen at once, so selector specs that drive the container directly see the writes synchronously. A microtask would have made every one of them asynchronous.

Why are Mendix values plain getters, not computeds?MobX

A computed that returns a Mendix value object compares it by identity and hides a change made in place. Every derivation reads gate.props itself.

Why does the database single selection keep a "loaded once" flag?parity

It reports unavailable until its datasource has loaded once, so the placeholder shows during the first load, as in the released widget. A pure derivation would show the bound value and then flicker to the datasource caption. A widget-level test from #2573 pins it.

Why does the options provider own all lazy-loading state?lazy loading

Limit, filter, bound-value lookup and the first-page latch depend on each other. With the latch in the Core, the result depended on whether downshift reported the open state or the typed text first. Now Core.open() calls requestFirstPage(), and ending a lookup, by a search or a page request, always asks for a full first page. Tests cover both orders.

Why no structural sharing in the view model?performance

Option content is a new React element on every pass, and no view memoises on its parts, so reusing slices by reference would save nothing. It belongs with memoised option rows, options shaped as { id, caption, content }, content cached per item, and comparer.shallow slices, tested by render counts.

Why does the editor preview still bundle MobX?bundle

The preview reuses the runtime Core over plain preview selectors, so preview and app share the view-model code and cannot drift. It costs about 90 KB in a file only Studio Pro loads. Extracting a pure view-model builder could drop it later.

What's next

Two refinements wait for the view split into parts, where memoised components make them pay off.

With the view split

Text-only changes

Structural sharing

Memoised option rows first, then per-item content caching and shallow-compared slices, verified with render-count tests.
